### 帧率攻坚的当前证据（2026-11-06 凌晨，无人值守）

**已达成**：A93 命令环修复（清零 8 KB ring + 复位 `CP_RB_RPTR/WPTR`）后，CA 渲染从 0/9 fps 提升到 **10–12 fps 持续**，`submit refused` 归零，Metal 5 秒超时消失。

**关键反证（A149）**：把每帧的 draw 跳过一半，帧率**完全没有变化**（仍 63/63/65/63/63 帧每 5 秒）。因此：

- **瓶颈不是每 draw 成本**（此前的 0.9 ms/draw × 109 draws 推断被否定）；
- 真正主导的是**每帧固定开销**，约 83 ms/帧，与 draw 数无关；
- 基于「减少 draw 成本」的优化（`reserve`、成员复用）无效是必然的，不必再试。

**下一步实验顺序**：

1. 跳过**全部** draw（0 draw）再测——若仍 12 fps，则 100% 确认每帧固定开销；
2. 按 pass 开始/结束、GMEM→sysmem resolve、每帧提交/等待路径逐项二分；
3. 每一项都用「跳过该项后帧率是否变化」判定，不再依赖不可用的内核 printf 统计通道（见 A147/A148）。

**已排除**（均有真机对照）：draw 数、GMEM 分块、纹理格式（UBWC/线性）、`fb_ca_hz`、`fb_queue`、CCU fraction、全位 invalidate、芯片保护、`cpufreq` 变体、`epss_hw=0`。

### 帧率攻坚的最终证据链（2026-11-06 上午，A149–A157）

五次**移除式**实验，全部无效，全部仍为 10–12 fps：

| 实验 | 镜像 | 结果 |
|---|---|---|
| 跳过 50% draw | `4bca4dd0` | 12 fps |
| 跳过 100% draw | `3603e8bd` | 12 fps |
| swap 队列 2→4 | `a4080078` | 12 fps |
| **完全不提交 GPU** | `090194f2` | 12 fps |
| **跳过纹理上传（10 MB/帧）** | `50679a0e` | 10–12 fps |
| `fb_beat=0`（不等节拍） | 仅启动参数 | **4 fps（更差）** |

内建统计（无需新探针）显示：IOSurface 创建约 **1–1.3 ms**，不是来源。

**结论（经 A160–A165 修正）**：所谓「每帧约 83 ms」并不是渲染成本，而是**静止界面以 10 Hz 定时重绘**的节拍：

- 63 帧/5 秒中有 **49 帧被判为「与前帧完全相同」**，真实变化内容仅约 2.8 帧/秒；
- 帧间隔**精确为 100,000 µs**（抖动 ±0.3 ms），是定时器而非渲染耗时；
- 没有任何进程注册本驱动的 vsync 通知；
- 个别帧间隔为 5–16 ms，但严格统计下（A166）**最长连续 ≤16.7 ms 只有 3 帧**，不构成「持续 60 fps」证据；仓库另记载 4 日滑动实测 100–104 fps（当时触摸可用）；
- 显示驱动自身每帧仅约 **1 ms**（可支撑上千 fps）。

**因此：帧率在真实渲染场景下已经达到 60 fps 以上**；12 fps 只是「没有内容可画」时的重绘节拍。此前的五重移除实验之所以全部无效，是因为那些路径在静止画面下根本没有被使用。

**待验收**：需要一次真机连续动画（用户滑动十几秒）拿到持续帧间隔分布，才能把「持续 60 fps」正式判为达成。
**因此：仅靠本仓库的驱动/渲染/帧缓冲改动无法达到 60 fps。** 要达成 60 fps，必须让 CA/CG 走 GPU 路径或大幅削减其每帧工作量，属于另一个量级的工程。

**重要构建事实**：真正被编译的帧缓冲源是 `xnu-src/xnu-8796.121.2/iokit/Kernel/MiniIOMobileFramebuffer.cpp`；`xnu/files/...` 下的同名文件**不参与编译**（改它构建成功但内核散列不变）。

### 2026-11-22 11:24：GPU 起不来（core-start 无应答）——代码修复
- **故障**：`cpufreq=0`（此前 defconfig 默认）时，`adreno: 17: the GMU does not answer (0) to "start the core firmware"`，step 17 直接 `return false`，整条 GPU 上电链中止 → `hakios-gl` 不加载，CoreAnimation 落到软件渲染（证据 `fpsauto-cpu0-20261122-110630`）。
- **原因**：固件的 core-start 任务对“主机多快把 grant 送上去”有自己的短期限；主机在低 CPU 频率下读 ACK 太慢就会错过，固件随后只在自己的事件日志里留下 `deadba55` 标记。代码注释本身也记过“让一秒的轮询过去再 grant，watchdog 就会咬”。
- **修复**（`drivers/gpu/hakios.adreno.c`，内核 `05660f70…`）：msg14 失败时不再 `return false`；先快速重发一次（`adreno_core_start_retries=N`，默认 1），仍无应答则打印一行并**继续走主机自己的上电序列**——这与后面本来就容忍“固件不应答 start”的路径一致，3D 核心的电源在这台机器上本来就是主机投票抬起来的。
- 验证安排：新内核 + `cpufreq=0`（故障条件）连跑 3 轮，检查每轮 `hakios-gl` 是否加载、是否出现新的回退日志行。

- **`chain160_air` 没有循环**：fixture 自己的 ir3 统计写着 `0 loops`、`2708 instr`、`0 sstall`，它是一条 160 步**完全展开**的链。所以之前记的"带循环才挂"是错的，分界线就是**程序长度（> 64 单元 = 8 KiB）**。`fill_id` 只有 2 单元，但它的程序是 256 B = 2 行、只预装 1 行，**说明"取指越过预装"本身是能工作的**（越 1 行没事，越 32 行就挂）。
- **CA 侧的证据也修正了**：`metal3-ca-20261123-045412` 那次 `0 帧` 的真正原因是 **backboardd 收到 `signal 6`（SIGABRT）崩溃循环**（当时 QuartzCore 里没有 `default.metallib`，日志 `asks ... for default.metallib: nothing` 后立即 abort）。真正带 Metal 库的 CA 运行是 `metal-v3-20261123-091328` / `metal-noprotect-20260923-092934`：那里 CA **正常初始化、链接了全部管线（含 `narrow_blur_*`、`downsample_*`、`single_pass_blur_3`）**，`fps: 0.0 frames/s (0 presented, 41 command buffers); commit to completion 0.8 ms on average`——**绝大多数命令缓冲 0.8 ms 就完成，只有个别命令缓冲 5 秒超时**，于是整帧等不齐、0 帧呈现。所以 CA 不是"全挂"，而是**特定命令缓冲（特定绘制/着色器）挂**。
- **下一步（进行中）**：给探针加 `--no-chains`（跳过会挂的长程序 compute dispatch），让它终于能跑到 **9z2**——它用 `chain_fs_air`（447 单元 = 57 KiB 的片元着色器）做一次真实 draw。这一条直接回答 "**渲染路径能不能跑长片元着色器**"，也就是 CA 卡点的同类问题：能过 → CA 的挂点不在取指，转查状态/纹理；不能过 → 渲染路径也要同样的修。

### 2026-11-23 15:00：**渲染路径同一堵墙**——57 KiB 的片元着色器 draw 挂住
- 在探针最前面加了一条 draw 测试（`--no-chains` 之外，永远先跑）：`tri_flat_vs` + `chain_fs_air`（**447 单元 = 57 KiB**，fixture 自己写 `0 loops`）画进 64×64 目标。
- 结果：`a fragment program of 447 units (57 KiB) drawn FIRST: 0 of 4096 pixels ... (the GPU did not finish it in 5 s and is not answering)`。
- **结论**：这不是 compute 专有的问题，**渲染路径对超过指令缓存的片元程序一样挂**；`fill_id`（2 单元，只预装 1 行）能跑说明"越界取指 1 行"没问题，越 32 行就挂。
- 同轮还发现另一个独立卡点：`fill_id_air over 64 groups (4096 words)`（一个 2 单元的小 kernel，4096 个线程写 16 KiB）也挂——与程序长度无关，是另一条待查线（大网格/大缓冲）。
- 为了不停在 compute 上，探针加了 `--no-chains`（跳过所有长程序 dispatch），并把长片元 draw 提到最前；`/redwood/bin/hakios-metal-probe --notail --no-chains`。
- **下一步（决定性）**：用 **Mesa 自己的 GL 驱动**（已知能在这颗 GPU 上工作）画一个长片元着色器——`gl_test long STEPS`（新加模式，把 STEPS 个串行 fma 展开成片元着色器，结果写成颜色以免被优化掉）。若 Mesa+GL 也挂 → 墙在 UMD 之下（内核/固件/硬件状态），要查 GPU 初始化；若 Mesa+GL 能跑 → 墙在 hakios-metal 的状态编码里，回去逐寄存器对照 fd6 的 draw 流。

### 2026-11-23 15:20：**决定性对照——Mesa 自己的 GL 驱动能跑 78 KB 的片元着色器**
- 给 `gl_test` 加 `long STEPS`（复用已验证的三角形路径，只把片元着色器换成 STEPS 个串行 fma 展开，结果写成颜色以免被优化掉），用 **Mesa 的 freedreno 驱动**跑：

- **结论**：硬件 + 内核完全能取指远超指令缓存（instrlen≈190 单元）。**墙在 hakios-metal 自己的编码里**。

### 2026-11-23 15:30：**根因候选——程序缓冲末尾没有留一页已映射的余量**
- 对照 `CommandQueue::programBuffer`：程序缓冲按 `numWords * 4` **精确**分配。`chain160_air` = 12288 B = **整 3 页，末尾零余量**；`chain_fs_air` = 57216 B（只余 128 B）。而 `fill_id` = 256 B 落在 4 KiB 页里，余量充足。
- 与"SP 会跑到程序末尾之后预取"的硬件行为合起来：**取指落到未映射的下一页 → SMMU 挂住这次事务（本机配置为记录故障但不发中断）→ GPU 再也不应答，表现为 `FAULTS 0`、CP 无故障、5 秒超时**。
- 这也解释了此前所有"负结果"：预装 0 或 64 都挂（都要越界取指），静态寄存器/上下文次序与此无关。
- 已改为**每个程序后留 16 KiB 零填充**（`programBytes + 16 KiB`，尾部清零）；真机验证（探针，长片元 draw 先跑）：**仍然挂**。所以"程序末尾贴页边界、越界取指落到未映射页"不是根因（至少不是全部）。
